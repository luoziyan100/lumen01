## 1. 当前核心判断

Lumen 现在已经能搜索论文，也能输出标题、作者、摘要、DOI、PDF 链接等元信息。但用户追问“这篇论文讲什么 / 方法是什么 / 结论是什么 / 局限是什么”时，系统缺少一个“针对搜索结果中的某篇论文进行浅读”的能力。

重要边界：

```text
临时读取 != 导入文献库
```

浅度研究和深度研究都可以下载开放 PDF，但默认只进入临时缓存。只有用户明确说“下载到本地 / 加入文献库 / 保存这篇 / 导入这些文章到文献库”，才进入永久文献库。

## 2. 现在的逻辑问题

### P1：搜索结果没有作为结构化状态保留下来

位置：
- `src/agent/types.ts`
- `src/agent/runtime.ts`
- `src/pages/ResearchPage.tsx`

现状：
- `SearchResult` 已有 `title / authors / abstract_text / open_access_url / source_url / doi / published_date`。
- 但 `ResearchAgentResult` 没有返回合并后的搜索结果列表。
- `ResearchPage` 只保存 assistant 文本，不保存 `lastSearchResults`。

影响：
- 用户问“这篇 / 第 2 篇 / 刚才那篇”时，planner 只能从聊天文本里猜指代对象。
- 后续 paper preview 无法稳定拿到 DOI、PDF URL、Semantic Scholar ID、OpenAlex URL。

建议：
- `ResearchAgentResult` 增加 `searchResults?: SearchResult[]` 或 `artifacts?: AgentArtifact[]`。
- `ResearchPage` 保存最近一轮搜索结果，例如 `lastSearchResults`，并传给 planner context。
- 搜索回复中显示的序号应和结构化结果数组一致。

### P1：intent 缺少 `paper_detail` / `paper_preview`

位置：
- `src/agent/types.ts`
- `src/agent/prompts.ts`
- `src/agent/runtime.ts`

现状：
```ts
type ResearchIntent =
  | 'academic_search'
  | 'local_research'
  | 'answer'
  | 'feedback'
  | 'clarify'
```

问题：
- `academic_search` 只能找论文。
- `local_research` 只能读已导入文献库的本地 PDF。
- 搜索结果里的开放 PDF 不属于本地文献库，也不是重新搜索。

建议新增：
```ts
type ResearchIntent =
  | 'academic_search'
  | 'paper_detail'
  | 'paper_preview'
  | 'deep_research'
  | 'import_to_library'
  | 'local_research'
  | 'answer'
  | 'feedback'
  | 'clarify'
```

阶段范围建议：
- 本阶段必须实现 `paper_detail` 和 `paper_preview`。
- `deep_research` 可以先只做接口和 prompt 边界，不必实现完整多篇深读。
- `import_to_library` 只做显式意图识别和安全边界，具体批量导入可以后续做。

### P1：prompt 没有识别“隐含阅读意图”

位置：
- `src/agent/prompts.ts`

用户不会总是说“读一下这篇”。更多真实表达是：

```text
这篇论文讲的是什么？
这篇论文的核心结论是什么？
它用了什么方法？
实验怎么做的？
它的贡献是什么？
有什么局限？
为什么重要？
它和第 1 篇有什么区别？
```

这些都应该被 planner 识别为：用户在追问某篇论文内容，需要 `paper_detail` 或 `paper_preview`。

建议 prompt 规则：
- 如果用户引用“这篇 / 那篇 / 第 N 篇 / 刚才那篇 / 某个标题 / 某个 DOI”，并询问内容、方法、结论、贡献、局限、实验、数据、理论、和其他论文关系，则选择 `paper_preview`。
- 如果用户只要作者、年份、DOI、期刊、摘要、链接，选择 `paper_detail`。
- 如果指代不明确，例如最近搜索结果里有多篇可能对象，选择 `clarify`，让用户选第几篇。

### P1：下载 PDF 和加入文献库的边界不清晰

现状：
- Lumen 有本地文献库 PDF import 能力。
- 但外部搜索结果没有“临时读取”工具。

必须遵守的产品规则：
- `paper_preview` 可以下载开放 PDF 到临时缓存，不进入文献库。
- `deep_research` 可以下载多篇开放 PDF 到临时缓存，不进入文献库。
- 只有用户明确要求“加入文献库 / 保存到文献库 / 导入本地 / 下载到本地文件”，才触发永久保存。
- 用户问“这篇讲什么 / 总结一下 / 方法是什么”不等于要求永久保存。

### P2：回答没有标注证据层级

位置：
- `src/agent/prompts.ts`

建议让回答明确区分：

```text
我基于搜索元信息和摘要回答。
我基于开放 PDF 的临时文本抽取回答。
我无法获取全文，只能基于摘要和元信息回答。
```

不要把 metadata/abstract 层级的回答说成“读了全文”。

## 3. 推荐目标架构

建议新增一条外部论文读取链路：

```text
academic_search
  -> searchResults artifact
  -> paper_detail
  -> paper_preview
  -> optional import_to_library
```

含义：
- `academic_search`：只负责找候选论文。
- `paper_detail`：不下载 PDF，增强元信息、摘要、TLDR、引用、链接。
- `paper_preview`：需要解释论文内容时，临时下载开放 PDF，抽取正文关键段落。
- `import_to_library`：只有用户明确要求时，把 PDF 变成永久文献库条目。

## 4. 数据结构建议

### 4.1 Agent context 增加最近搜索结果

```ts
interface AgentInputContext {
  currentDate: string
  timezone: string
  hasLocalPapers: boolean
  localPaperCount: number
  activeProjectName?: string
  selectedPaperTitle?: string
  lastSearchResults?: SearchResult[]
}
```

注意：
- 传给模型时可以裁剪字段，只保留序号、title、authors、year/published_date、doi、source_url、open_access_url、abstract snippet。
- 不要把超长摘要无限塞进 planner。

### 4.2 Search result artifact

建议 runtime 在搜索后返回 artifact：

```ts
interface AgentArtifact {
  type: 'search_results' | 'paper_detail' | 'paper_preview'
  id: string
  createdAt: string
  data: unknown
}
```

也可以先简单做：

```ts
interface ResearchAgentResult {
  reply: string
  searched: boolean
  plan: SearchPlan
  searchResults?: SearchResult[]
  ...
}
```

先简单，后续再抽象 artifacts。

### 4.3 Paper reference

```ts
interface PaperReference {
  resultIndex?: number
  title?: string
  doi?: string
  sourceUrl?: string
  openAccessUrl?: string
}
```

planner 对“第 2 篇 / 这篇 / 刚才那篇”做解析，runtime 再用 `lastSearchResults` 映射到具体 paper。

## 5. 工具设计

### 5.1 paper_detail tool

目标：不下载 PDF，补充可公开获得的元信息。

输入：
```ts
interface PaperDetailInput {
  paper: PaperReference
}
```

输出：
```ts
interface PaperDetail {
  title: string
  authors: string[]
  year?: number
  publishedDate?: string
  venue?: string
  doi?: string
  abstract?: string
  tldr?: string
  citationCount?: number
  sourceUrls: string[]
  openAccessPdfUrl?: string
}
```

数据源优先级：
- Semantic Scholar paper detail：适合 abstract、authors、citationCount、openAccessPdf、externalIds。
- OpenAlex work：适合 abstract inverted index、authorships、OA location。
- Crossref：适合 DOI、publisher、journal、published date。
- arXiv：适合 arXiv 摘要和 PDF。

本阶段不要求所有源都完美；可以优先用已有 `SearchResult`，再按 DOI/title 补一次 detail。

### 5.2 paper_preview tool

目标：对单篇开放 PDF 做临时浅读，不导入文献库。

触发：
- 用户追问某篇论文的内容、方法、结论、贡献、局限、实验、理论。
- 用户没有说“下载到本地/加入文献库”，但语义上需要读正文。

流程：
```text
resolve paper reference
-> ensure paper detail
-> if abstract/detail 足够回答：可直接回答并说明证据层级
-> if 需要正文且有 openAccessPdfUrl：下载 PDF 到临时缓存
-> 抽取文本
-> 截取关键段落：Abstract / Introduction / Method / Experiments / Results / Discussion / Limitations / Conclusion
-> 让模型基于片段回答
```

如果没有开放 PDF：
- 不要建议 Sci-Hub。
- 说明无法获取开放全文，只能基于摘要/元信息回答。
- 可提示用户导入 PDF 后再深读。

### 5.3 temp cache

建议位置：

```text
~/.lumen/cache/paper-preview/
  metadata.sqlite 或 metadata.json
  pdf/
  text/
```

如果 Tauri 有 app cache dir，优先使用应用缓存目录，不要硬编码用户路径。

缓存策略：
- 默认 TTL：7 天。
- 默认最大容量：500MB 或 1GB。
- 清理策略：LRU，最近未访问的先删。
- 文件名：用 DOI / source id / URL hash，避免非法字符。
- 缓存命中时复用 text，不重复下载和解析。

安全边界：
- 只下载 `http/https` 开放 PDF URL。
- 限制文件大小，例如 50MB。
- 校验响应 `Content-Type` 尽量像 PDF；不满足则拒绝或降级。
- 不执行 PDF 内任何内容，只做文本解析。

### 5.4 import_to_library tool

本阶段原则：
- 可以先不实现完整导入，但 planner 必须能识别显式导入意图。
- 如果用户说“把第 2 篇加入文献库 / 保存这篇 PDF / 下载到本地文件”，才进入导入流程。
- 如果用户只是问“讲什么 / 结论是什么 / 方法是什么”，绝不能导入文献库。

后续可以做：
```text
library_curator_agent
```

它根据用户多轮追问判断兴趣，最多建议：

```text
你连续追问了第 2 篇论文的方法和结论，要不要把它加入文献库？
```

但不能自动导入。

## 6. Planner prompt 更新要求

Planner available tools 建议改成：

```ts
availableTools: [
  { name: 'direct_answer', whenToUse: '普通问答、时间日期、闲聊、能力说明', cost: 'low' },
  { name: 'academic_search', whenToUse: '用户要求找外部论文、最新论文、验证文献或补充研究材料', cost: 'high' },
  { name: 'paper_detail', whenToUse: '用户问搜索结果中某篇论文的作者、摘要、链接、DOI、期刊、年份等元信息', cost: 'medium' },
  { name: 'paper_preview', whenToUse: '用户问搜索结果中某篇论文讲了什么、方法、结论、贡献、局限、实验或理论，即使没有说“读”', cost: 'high' },
  { name: 'read_local_papers', whenToUse: '用户明确要求分析已经导入本地文献库的论文、集合或项目', cost: 'high' },
  { name: 'import_to_library', whenToUse: '用户明确要求保存、导入、加入文献库或下载到本地文件', cost: 'high' },
  { name: 'clarify', whenToUse: '用户指代不清或意图不足以选择工具', cost: 'low' },
  { name: 'feedback', whenToUse: '用户评价或纠正上一轮结果', cost: 'low' },
]
```

必须加入的规则：
- 用户说“这篇论文讲什么 / 结论是什么 / 方法是什么 / 实验是什么 / 局限是什么 / 贡献是什么”，属于 `paper_preview`，不要求用户显式说“读”。
- 用户说“作者是谁 / 哪年发表 / DOI 是什么 / 有没有 PDF / 摘要是什么”，属于 `paper_detail`。
- 用户说“保存 / 加入文献库 / 下载到本地 / 导入这些文章”，才属于 `import_to_library`。
- `paper_preview` 和 `deep_research` 默认只写临时缓存，不进入文献库。
- 如果“这篇”无法解析到唯一搜索结果，选择 `clarify`。

## 7. Runtime 行为建议

建议新增分支：

```ts
if (plan.intent === 'paper_detail') {
  resolvePaperReference(...)
  runPaperDetailTool(...)
  synthesizePaperDetailAnswer(...)
}

if (plan.intent === 'paper_preview') {
  resolvePaperReference(...)
  runPaperPreviewTool(...)
  synthesizePaperPreviewAnswer(...)
}

if (plan.intent === 'import_to_library') {
  requireExplicitImportIntent(...)
  importPaperToLibrary(...)
}
```

注意：
- `paper_preview` 使用 `synthesizer` 或 `local_paper_analysis` 级别模型，不要用 planner 模型生成最终解释。
- trace 要记录证据层级：`metadata_only`、`abstract_only`、`pdf_text_preview`、`full_local_pdf`。
- 如果 PDF 下载失败，不要把整个 agent run 标 failed；降级到 metadata/abstract，并在回答里说明。

## 8. 输出协议

回答论文内容时，建议固定包含：

```text
证据来源：metadata / abstract / PDF 临时文本 / 本地文献库全文

这篇论文主要讲什么：
...

核心方法：
...

主要结论：
...

局限或注意事项：
...
```

如果只是 metadata/abstract：

```text
我目前只能基于摘要和元信息解释，还没有读取全文。
```

如果临时读取了 PDF：

```text
我临时读取了开放 PDF 的文本片段，但没有把它加入你的文献库。
```

如果用户可能想保存：

```text
如果你想长期保存这篇论文，我可以把它加入文献库。
```

## 9. 验收用例

前置：先搜索一组论文，使页面有 `lastSearchResults`。

必须通过：
- 用户问“第 2 篇论文讲的是什么？” -> 解析到第 2 条搜索结果，执行 `paper_preview` 或 `paper_detail` 后回答。
- 用户问“这篇用了什么方法？” -> 如果最近只有一个明确目标，执行 `paper_preview`；如果不明确，追问是哪一篇。
- 用户问“它的作者是谁？” -> 执行 `paper_detail`，不下载 PDF。
- 用户问“把第 2 篇加入文献库” -> 只有这时才触发 `import_to_library`。
- 用户问“总结一下第 2 篇” -> 可以临时下载 PDF，但不能出现在文献库列表里。
- 用户问“这几篇做一个深入对比” -> 本阶段可以提示 deep research 尚未完整实现，或临时读取多篇，但仍不得导入文献库。

必须不发生：
- 不能因为用户问“讲什么”就永久保存 PDF。
- 不能没有读 PDF 却说“我读了全文”。
- 不能搜索结果指代不清时乱选一篇。
- 不能建议 Sci-Hub。

## 10. 实施顺序建议

1. 让搜索结果以结构化 `searchResults` 返回到页面，并保存为 `lastSearchResults`。
2. Planner context 加入裁剪后的 `lastSearchResults`。
3. 扩展 intent/schema：`paper_detail`、`paper_preview`、`import_to_library`。
4. 先实现 `paper_detail`：基于已有 SearchResult + DOI/title 补元信息。
5. 再实现 `paper_preview`：开放 PDF 临时下载、文本抽取、缓存。
6. 在 runtime 中新增 `paper_detail` / `paper_preview` 分支。
7. 加输出证据层级说明。
8. 最后再考虑显式导入文献库；如果时间不够，本阶段至少要做到“不自动导入”。

## 11. 非本阶段范围

- 自动根据用户兴趣把论文加入文献库。
- 完整多轮 deep research agent。
- 引文网络自动构建。
- PDF 视觉模型阅读。
- 对非开放获取论文绕过付费墙。
