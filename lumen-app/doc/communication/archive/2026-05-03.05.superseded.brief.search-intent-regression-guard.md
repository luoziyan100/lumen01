## 1. 用户复现

用户在 app 中输入类似：

```text
搜索上周 AI 领域相关论文
```

Lumen 先回复“我会使用外部学术数据库检索，请稍候”，但没有真正给出搜索结果。用户追问“结果呢 / 你不能搜索吗”，Lumen 又回答：

```text
我作为 Lumen 深度研究助手，无法直接执行实时学术搜索...
我的核心能力是深度分析你文献库中的论文...
```

这说明当前请求没有进入 `runSearchPipeline()`，而是被 planner/runtime 落到了 `answer` 或 `local_research` / `direct_answer` 路径。

## 2. 根因判断

这不是搜索后端不可用，而是搜索意图被上游吞掉。

当前代码有两个高风险断点：

1. `normalizePlan()` 要求 `queries.length > 0` 才允许 `shouldSearch=true`。
2. `enrichPlanWithSearchMode()` 一看到 `plan.searchMode` 就直接返回，不再执行 deterministic feed fallback。

于是下面几种 planner 输出都会导致不搜索：

```json
{
  "intent": "academic_search",
  "shouldSearch": true,
  "queries": [],
  "searchMode": "recent_ai_feed",
  "arxivCategories": ["cs.AI", "cs.LG"]
}
```

归一化后 `shouldSearch=false`，然后因为 `searchMode` 已存在，兜底不会补 query。

```json
{
  "intent": "answer",
  "shouldSearch": false,
  "queries": [],
  "searchMode": "keyword_search",
  "response": "好的，我将帮你搜索..."
}
```

因为 `searchMode` 已存在，兜底不会把“上周 AI 论文”强制改成 `recent_ai_feed`，runtime 直接返回 response 或走 `direct_answer`。

## 3. P0 Finding: feed plan 没 query 会被 normalize 成不搜索

位置：

- `src/agent/guides.ts:128-131`

现状：

```ts
shouldSearch: Boolean(raw.shouldSearch) && queries.length > 0
```

问题：

`recent_ai_feed` / `arxiv_category_feed` 的核心输入是 categories + timeRange，不应该必须依赖 `queries`。现在 planner 只要没填 query，就算 searchMode 和 categories/timeRange 都对，也会被改成 `shouldSearch=false`。

建议：

```ts
const rawSearchMode = ...
const isFeedMode = rawSearchMode === 'recent_ai_feed' || rawSearchMode === 'arxiv_category_feed'
const shouldSearch = Boolean(raw.shouldSearch) && (queries.length > 0 || isFeedMode)
```

并为 feed mode 补默认 query：

```ts
queries: queries.length > 0
  ? queries
  : isFeedMode
    ? ['arXiv category feed']
    : []
```

## 4. P0 Finding: `if (plan.searchMode) return plan` 阻断确定性兜底

位置：

- `src/agent/guides.ts:180-182`

现状：

```ts
function enrichPlanWithSearchMode(input, plan) {
  const text = input.userText
  if (plan.searchMode) return plan
  ...
}
```

问题：

planner 很容易在无关 intent 下填一个默认 `searchMode: "keyword_search"`，或者填 `recent_ai_feed` 但漏 query。此时 deterministic fallback 被提前跳过，明确搜索请求最终进入 `answer/local_research/direct_answer`。

建议：

- 不要因为 `plan.searchMode` 存在就直接返回。
- 先判断 `asksRecentFeed` / explicit external search。
- 如果用户文本明确是“搜索/找/检索/最新论文/上周论文/arXiv feed”，就强制修正：

```ts
if (asksRecentFeed && categoryInfo) {
  return {
    ...plan,
    intent: 'academic_search',
    shouldSearch: true,
    queries: plan.queries.length > 0 ? plan.queries : [`arXiv ${categoryInfo.preset} recent feed`],
    searchMode: categoryInfo.preset === 'custom' ? 'arxiv_category_feed' : 'recent_ai_feed',
    ...
  }
}
```

只有当不是明确 feed/search 请求时，才保留已有 `plan.searchMode`。

## 5. P1 Finding: explicit search 请求不应落入 direct_answer

位置：

- `src/agent/runtime.ts:670-679`

现状：

```ts
if (!plan.shouldSearch) {
  return chatWithAgentModel(input.history, 'simple_answer')
}
```

问题：

当用户明确说“搜索上周 AI 论文”，但 planner 失败或误判成 `answer/local_research` 时，runtime 把请求交给普通聊天模型。普通模型看到系统 prompt 里的“文献库为空 / Search Agent 负责搜索”，就容易自我否定，说“我无法实时搜索”。

建议增加 runtime guard：

```ts
if (!plan.shouldSearch && looksLikeExternalSearchRequest(input.userText)) {
  const forcedPlan = deterministicExternalSearchPlan(input)
  if (forcedPlan) {
    plan = forcedPlan
  } else {
    return clarify("你想搜索哪个外部论文主题？")
  }
}
```

原则：

- 明确外部搜索请求不能进入 `direct_answer`。
- 如果无法构造搜索 plan，宁可 clarify，也不要让模型说“我不能搜索”。

## 6. P1 Finding: local_research 不应处理明确外部搜索

位置：

- `src/agent/runtime.ts:640-667`

问题：

截图里“文献库为空 / 核心能力是分析文献库”很像进入了 `local_research` 或 `direct_answer`。如果用户文本包含“搜索、找论文、最新、上周、arXiv、OpenAlex、Semantic Scholar”等外部搜索信号，runtime 应阻止 `local_research` 执行。

建议：

```ts
if (plan.intent === 'local_research' && looksLikeExternalSearchRequest(input.userText)) {
  plan = deterministicExternalSearchPlan(input) ?? { intent: 'clarify', ... }
}
```

## 7. 建议实现

新增纯函数，避免散落 regex：

```ts
function looksLikeExternalSearchRequest(text: string): boolean
function deterministicExternalSearchPlan(input: RunResearchHarnessInput, base?: SearchPlan): SearchPlan | null
```

它应覆盖：

- 搜索/找/检索 + 论文/文献
- 最新/最近/本周/上周/某日期以来 + AI/LLM/机器学习/arXiv
- arXiv / OpenAlex / Semantic Scholar / Crossref 明确源
- “上周 AI 领域相关论文”

对于 recent feed，仍走：

```text
searchMode=recent_ai_feed
sourceHint=arxiv
categoryPreset=ai
arxivCategories=["cs.AI","cs.LG","cs.CL","cs.CV","cs.RO","stat.ML"]
timeRange=最近 7 天或用户指定日期
sortMode=newest
feedLimit=50/100
includeTotalCount=true/false
```

## 8. 不要修成另一个回归

注意保留上一阶段 Result Set Memory 的规则：

- 如果用户说“刚才那 10 篇 / R1 前 5 篇 / 它们的链接”，优先复用结果集，不要强制搜索。
- 只有明确“重新搜 / 再搜 / 换一批”才开启新搜索。

也就是说优先级应是：

```text
1. result set reference resolver
2. explicit force-new-search phrase
3. explicit external search guard
4. planner model output
5. direct_answer / local_research
```

## 9. 验收用例

必须通过：

1. 新对话输入“搜索上周 AI 领域相关论文”。
   - 必须出现 `结果集 R1`。
   - 必须执行 `recent_ai_feed` 或等价 arXiv category feed。
   - 不能回复“我无法实时搜索”。
2. 追问“结果呢”。
   - 如果搜索已经完成，解释/展示 R1。
   - 如果搜索还在运行，应显示真实 loading，不生成假承诺。
3. 输入“你不能搜索吗？”
   - 应说明“可以搜索，刚才是路由错误/未触发搜索”或重新触发搜索。
   - 不能说“核心能力只分析文献库”。
4. 搜索完成后问“R1 前 5 篇做报告”。
   - 仍使用 R1，不重新搜索。
5. 问“重新搜一批上周 AI 论文”。
   - 创建 R2。
