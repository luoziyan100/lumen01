## 0. Why this PR exists

我们现在在测试 Lumen Research Agent，但很多问题无法判断是：

```text
A. 模型能力不够 / JSON 跟随能力不稳 / 推理质量不够
B. Lumen 架构、planner、reference binding、tool routing 本身有问题
```

所以需要把 Lumen 的默认模型临时切到 OpenAI GPT 系列里的高能力模型，用 **OpenClaw 已有的 OpenAI Codex OAuth 授权**，而不是再要求用户填 OpenAI Platform API Key。

本 PR 的目标不是做完整商业化 auth 系统，而是给本地 dev/testing 提供一个可靠模型通道：

```text
Lumen dev app
→ provider = openai-codex
→ Vite dev server reads OpenClaw auth profile server-side
→ calls https://chatgpt.com/backend-api/codex/responses
→ parses SSE text
→ returns normal { content } to Lumen
```

## 1. Ground truth discovered before this brief

### 1.1 Current Lumen AI path

Current code is API-key based:

- `src/services/ai.ts`
- `src/services/ai-config.ts`
- `src/pages/SettingsPage.tsx`
- `vite.config.ts` `/api/ai/chat`
- `src-tauri/src/commands/ai_config.rs`

Existing shape:

```text
Settings page saves provider + api_key + default_model
→ chatWithAI()
→ in browser dev, POST /api/ai/chat
→ vite.config.ts calls OpenAI/DeepSeek/Anthropic/custom endpoint
```

There is no OAuth concept in Lumen today.

### 1.2 Current OpenClaw auth state

On this machine, OpenClaw already has `openai-codex` OAuth profiles and model rows:

```text
openai-codex/gpt-5.5
openai-codex/gpt-5.4
openai-codex/gpt-5.3-codex
```

Auth profile store:

```text
~/.openclaw/agents/main/agent/auth-profiles.json
```

Important: do **not** print this file or leak tokens to frontend logs.

### 1.3 Direct backend requirements verified live

The Codex Responses backend endpoint is:

```text
https://chatgpt.com/backend-api/codex/responses
```

Observed hard requirements:

- `instructions` is required.
- `store` must be `false`.
- `stream` must be `true`.
- `max_output_tokens` is rejected by this backend in this path.

A minimal successful body shape:

```json
{
  "model": "gpt-5.5",
  "instructions": "You are a concise assistant.",
  "input": [
    {
      "role": "user",
      "content": [
        { "type": "input_text", "text": "Say exactly: pong" }
      ]
    }
  ],
  "stream": true,
  "store": false,
  "reasoning": { "effort": "none" }
}
```

Observed SSE events include:

```text
response.created
response.in_progress
response.output_item.added
response.content_part.added
response.output_text.delta
response.output_text.done
response.content_part.done
response.output_item.done
response.completed
```

Text should be collected from `response.output_text.delta` events. `response.output_text.done` contains the final text too, but use delta accumulation as primary.

## 2. Scope

### Implement

Add a new local/dev provider:

```text
provider id: openai-codex
UI name: OpenAI GPT OAuth / OpenAI Codex OAuth
model hint: gpt-5.5
fallback model for manual testing: gpt-5.4
```

Use it to run all Lumen agent roles through the same configured GPT model unless explicitly overridden.

### Do not implement in this PR

- Do not build a full OpenAI OAuth login UI inside Lumen.
- Do not call `codex exec`.
- Do not use `mindcode-claw-image2` style generated-image directory scanning.
- Do not copy OpenClaw refresh tokens into Lumen storage.
- Do not send OpenClaw access tokens to the browser.
- Do not make this production auth architecture. This is a local dev/testing bridge.

## 3. Required code changes

## 3.1 MODIFY `src/services/ai.ts`

### Add provider row

Add a provider entry:

```ts
{ id: 'openai-codex', name: 'OpenAI GPT OAuth', modelHint: 'gpt-5.5', placeholder: 'OpenClaw profile id（可选）' }
```

The API key field for this provider should be treated as an optional OpenClaw profile selector, not a secret API key.

Examples of acceptable values:

```text
(empty)                         → choose default usable openai-codex profile
openai-codex:zluo5820@gmail.com → choose that exact profile id
zluo5820@gmail.com              → choose profile by email
```

### Fix `chatWithAgentModel()` role options

Current behavior only applies role-specific planner/synthesizer options for DeepSeek. For non-DeepSeek providers it calls:

```ts
return chatWithAI(messages, undefined, signal)
```

That loses important role options like:

```ts
planner: { temperature: 0, maxTokens: 1200, responseFormat: 'json' }
synthesizer: { temperature: 0.2, maxTokens: 4096 }
```

Modify so role options apply to every provider.

Desired behavior:

```ts
const roleOptions = AGENT_ROLE_OPTIONS[role]

if (config.provider === 'deepseek') {
  return chatWithAI(messages, {
    ...roleOptions,
    provider: 'deepseek',
    model: DEEPSEEK_ROLE_MODELS[role],
    signal,
  })
}

return chatWithAI(messages, {
  ...roleOptions,
  provider: config.provider,
  signal,
})
```

For `openai-codex`, `maxTokens` may be ignored by the dev proxy because the backend rejects `max_output_tokens`; still keep role options in the call shape so other providers keep working.

### `chatWithAI()` missing config behavior

For `openai-codex`, do not require a real API key. It is okay if `config.api_key` is empty/null as long as provider is `openai-codex`.

Recommended condition:

```ts
if (!config) throw new Error('请先在设置中配置 AI 模型')
if (config.provider !== 'openai-codex' && !config.api_key) {
  throw new Error('请先在设置中配置 AI API Key')
}
```

In browser dev (`!hasTauriInvoke()`), route `openai-codex` through `/api/ai/chat` like other providers.

In Tauri packaged mode, it is acceptable in this PR to throw a clear unsupported message:

```text
OpenAI Codex OAuth 暂只支持本地 dev server 测试，请使用 http://127.0.0.1:5173/。
```

Unless you choose to also implement a Tauri command. Do not expand scope unless necessary.

## 3.4 MODIFY `vite.config.ts` `/api/ai/chat`

Add server-side support for:

```text
request.provider === 'openai-codex'
```

### Request validation

Current validation requires `request.apiKey`. Change it so `openai-codex` does not require `apiKey`:

```ts
if (!request.provider || !Array.isArray(request.messages)) ...
if (request.provider !== 'openai-codex' && !request.apiKey) ...
```

### Auth profile resolution

Implement server-side helper to read OpenClaw auth profile.

Recommended env/config behavior:

```text
OPENCLAW_STATE_DIR       default: ~/.openclaw
LUMEN_OPENCLAW_AGENT_ID  default: main
```

Default auth path:

```text
${OPENCLAW_STATE_DIR}/agents/${LUMEN_OPENCLAW_AGENT_ID}/agent/auth-profiles.json
```

Profile selection:

1. If `request.apiKey` is non-empty, treat it as profile selector:
   - exact profile id match, or
   - email match.
2. Else choose the first usable `openai-codex` profile.
3. Usable means:
   - `provider === 'openai-codex'`
   - `type === 'oauth'`
   - has `access`
   - `expires` is missing or in the future.

If no usable profile exists, return a clear error:

```text
No usable OpenClaw openai-codex OAuth profile found. Run: openclaw models auth login --provider openai-codex
```

Do not log access or refresh tokens.

### Convert Lumen messages to Codex Responses input

System messages:

- Combine all `role === 'system'` content into `instructions`.
- If no system message exists, use a short default:

```text
You are Lumen's research assistant. Follow the user request precisely.
```

Non-system messages:

Map to Responses input messages:

```ts
{
  role: message.role === 'assistant' ? 'assistant' : 'user',
  content: [{ type: 'input_text', text: message.content }]
}
```

Images can be ignored in this first PR unless easy to support. If ignored, fail clearly when `message.images?.length` exists:

```text
openai-codex dev proxy does not support image inputs yet
```

### Call Codex Responses backend

Endpoint:

```text
https://chatgpt.com/backend-api/codex/responses
```

Headers:

```ts
{
  'Content-Type': 'application/json',
  'Authorization': `Bearer ${profile.access}`,
}
```

Body:

```ts
{
  model: request.model?.trim() || 'gpt-5.5',
  instructions,
  input,
  stream: true,
  store: false,
  reasoning: { effort: 'none' }
}
```

Important:

- Do not send `max_output_tokens`; observed backend rejects it.
- Do not send `store: true` or omit `store`; observed backend requires `store: false`.
- Do not send `stream: false`; observed backend requires `stream: true`.
- Temperature may be ignored or omitted. Prefer omit unless required.

For `request.responseFormat === 'json'`, strengthen `instructions`:

```text
Return a single valid JSON object only. Do not wrap it in markdown.
```

Do not rely on unsupported response-format fields unless you verify them live.

### Parse SSE

Parse event stream blocks separated by blank lines.

Collect text from JSON events where:

```ts
event.type === 'response.output_text.delta'
```

Append `event.delta` to output.

If no deltas are found, fallback to `response.output_text.done` text if present.

If backend returns non-200, surface status and body in error, but redact tokens.
